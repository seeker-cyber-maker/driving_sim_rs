# ALD experiment contract

## Modes and limits

- **Train a population** evolves candidates using the selected reward and training settings. Training result roles such as fitness winner, fastest lap, or clean-lap candidate are defined by the app; unavailable roles must stay unavailable.
- **Frozen evaluation** drives one policy with unchanged weights. It does not produce a new winner population. For a direct same-backend policy comparison, match vehicle, track, horizon, controller frequency, collision/idle settings, backend, math profile and engine build. For an explicitly requested CPU/GPU comparison, vary only the backend intentionally; hold frozen input bytes, vehicle, track hash, requested ticks, decision rate, collision/idle settings, engine build and math profile exact. Keep an incompatibility visible when conditions differ; do not widen a numerical tolerance after seeing a mismatch.
- CPU is the anonymous default and uses no GPU allowance. Per-run documented caps are 4,000,000 CPU vehicle-ticks / 25 seconds and 8,000,000 GPU vehicle-ticks / 45 seconds; both cap analysis at 32,768 car-generation rows. Respect smaller current UI limits if shown. Calculate projected vehicle-ticks as population × generations × ticks per generation, and analysis rows as population × generations before starting.
- The app's first-run starter is 32 cars × 20 generations × 900 ticks, 60 decisions/s (15 simulated seconds per car/generation), mutation 0.3. This is a selectable starting configuration, not a guarantee of a fast or clean lap. CPU and GPU run limits differ; never infer a run's effective settings from the defaults when its receipt is available.
- Physics timing is 60 Hz. Policy decision rate is a separate setting with 60, 30, and 15 decisions per second; the current default is 60. Preserve the user's declared rate, and report both physics and decision rates. The native replay is a fresh CPU drive at 60 Hz decisions, so its frequency can differ from training/evaluation. Check current visible controls/readiness before a run.
- Keep requested ticks separate from actual elapsed ticks and statistics updates in the result. For example, the qualified 900-requested-tick fixture reports 906 elapsed ticks. Compare the recorded values as supplied; do not relabel the requested horizon as exact executed duration or edit records to make them match.
- In the published package, `build_id` content-addresses `RELEASE_MANIFEST.json`, whose members include the native simulator and GPU library hashes. A matching receipt build ID binds the service-reported native package identity; it is not independent hardware attestation. Keep native hashes from the public source/capabilities when available. On another deployment, verify that its build ID has this binding or mark native-engine identity unverified.

## Networks and tracks

- Supported vehicle types are Formula (Type 0), Rally (Type 1), Snowmobile (Type 2), and Truck (Type 3). Fresh networks require Steering and Acceleration. Snowmobile does not support Handbrake and has at most four outputs; Formula, Rally, and Truck support at most five. Imported types and output order belong to the imported network; inspect rather than silently convert them.
- Runner network limits: up to 20 inputs, 12 total layers, 16 nodes per hidden layer; supported sensor types use the app's original-game defaults when optional parameters are omitted. These bounds do not imply support for arbitrary modified-game networks.
- Built-in Replica tracks are reconstructed tile/terrain references, not official files or full physics replicas. The map is a layout/terrain preview, not live driving or collision geometry. A successful run or challenge prediction is not an original-game star, official leaderboard result, or parity proof.
- Track selection is shared between Run & results and Training & recipes. Confirm the final visible selection on both surfaces when relevant. A built-in selection and an uploaded custom track have different input provenance; record which was used.

## GPU gate

GPU is optional and must be requested by the user. Before choosing GPU or submitting a job, inspect current account allowance using the normal authenticated [HF billing interface](https://huggingface.co/settings/billing) and retain a quota observation/receipt no more than five minutes old for the current account and deployment. Allowance is time-sensitive; refresh stale evidence. Record observation time, used/total/remaining included seconds, declared call seconds, size multiplier, reserve, admission result and expiry. Never include credentials or billing screenshots in public results.

The current app declares `@spaces.GPU(duration=90)`. Its conservative release-check admission envelope is **90 seconds × hardware-size factor + 210 seconds reserve**. Verify the deployment's actual decorator/reservation and [current HF size/quota rules](https://huggingface.co/docs/hub/spaces-zerogpu#technical-specifications): at this release, large costs 1× and xlarge 2×. The reserve is the conservative experiment budget, not a provider fee. Keep this envelope distinct from the app's execution-time limit. Unknown reservation, size/cost or included allowance means no GPU dispatch.

Do not spend paid overage, change an account plan, or treat account sign-in as authorization for bucket access. If the user requested GPU and a gate fails, stop rather than silently switch to CPU. Use only the authorized retry budget. A clearly failed attempt may be retried within that budget after refreshing quota evidence. A prior uncertain dispatch still occupies its authorized attempt until reconciled through visible job state; fresh quota never authorizes a duplicate call.

Use the app's normal HF sign-in flow only if needed and authorized for account GPU allowance; verify the actual requested scope before accepting. The app may reload during sign-in, so re-check driver, track, settings, and mode afterward. A bounded retry budget may be preauthorized by the user; do not ask again for retries already within that budget. If dispatch may have occurred, reconcile visible job state before any retry. Never blindly retry an uncertain call, ask for or paste access tokens or credentials, or grant optional private-bucket/repository access merely to run experiments.
