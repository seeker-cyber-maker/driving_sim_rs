# Run an ALD experiment

Use this skill for the ALD Hugging Face training lab. Use the ALD deployment the user names; if they do not name one, start at [the public GPU app](https://tiga-rce-ald-tao-gpu.hf.space/). Confirm the selected page is the intended ALD app and keep identity, quota, and evidence tied to that deployment. A failure on a supplied deployment does not authorize switching to another host, account or compute backend. It covers Formula, Rally, Snowmobile, and Truck on built-in replica tracks. It does not operate the original game, establish full game parity, qualify Godot/Swift integrations, or deploy models.

1. Translate the user's goal into one experiment: choose **Train a population** to evolve candidates or **Frozen evaluation** to measure one unchanged network. Identify the source driver, vehicle, replica/custom track, horizon, and outputs they want. Keep the user's baseline intact. Do not promote or replace it unless the user explicitly asks for promotion and every gate they declared has passed; a training result or comparison alone is not promotion evidence.
2. Prefer anonymous CPU unless the user specifically requests GPU. Choose a bounded configuration that fits the app's current limits and the user's goal. A practical starting example is 8 cars × 3 generations × 900 ticks at the user's declared decision rate; for frozen evaluation, start with one policy × 900 ticks. These are workflow examples, not training optima. Preserve any user-declared decision rate. If it is unspecified, use the live UI default (currently 60 decisions/s) and state it. Physics runs at 60 Hz; policy decisions can be set to 60, 30, or 15 per second. Do not silently expand work. Agree on a bounded attempt/retry budget before GPU calls; use it without repeatedly asking after clearly failed attempts, but reconcile any uncertain dispatch from visible job state before retrying and never submit blindly.
3. Discover the live app's optional agent tools from the current page and read their descriptions before use. Use them only for supported local status/navigation/inspection actions. For remote training, frozen evaluation, recording, account actions, storage, and deletion, use the visible app controls and ordinary browser/file dialogs. If those tools are unavailable, use visible labels and controls; never assume old tool IDs, hidden state, or page scripts.
4. For GPU, require an explicit GPU request. Inspect the current authenticated Hugging Face allowance using the account's normal billing UI; keep a fresh quota observation/receipt no more than five minutes old at admission, and refresh it when stale or when account/deployment changes. Calculate admission as declared GPU seconds × the current HF hardware-size multiplier + reserve seconds. For the current release example, that is 90 seconds × the size factor (currently large 1× and xlarge 2×) + 210 seconds reserve; verify the current factor and remaining allowance rather than carrying these values to another deployment. This quota envelope is separate from the app's per-run execution caps. Proceed only when the planned call fits included quota. The app's sign-in may reload the page, so sign in before choosing files. Use included allowance only; stop if quota is insufficient or paid overage is offered. Never request or enter a personal access token, and do not authorize bucket/repository access for a run.
5. Before starting, review the visible vehicle, track, compute, mode, settings and projected work. State whether a clean-driving request means assessing the baseline or evolving a candidate, and use the user's recipe or visible supported reward controls rather than inventing a reward contract. Then start only the user-authorized run. Save the received primary network, paired analysis/report, receipt, and visible run identity/build evidence where available. Read [references/results-and-replay.md](references/results-and-replay.md) for claim and artifact checks.
6. When the user requests replay verification, record the received candidate in a fresh CPU drive, choose the requested 5- or 15-second duration, then play/pause/scrub/step and inspect the measured controls and consumed sensors. This is an additional CPU simulation; do not record unless it is within the user's requested scope.
7. Report what actually completed, preserve failed or incomplete evidence, and separate UI acknowledgements from independently confirmed server deletion. If a run fails, quota is exhausted, artifacts do not match, or the app cannot verify receipt/cleanup, stop and report that state. Do not exceed the user-authorized retry budget. For GPU retries, refresh quota evidence; if dispatch may have occurred, reconcile visible job state before retrying.

Use [references/experiment-contract.md](references/experiment-contract.md) when choosing settings, vehicles, tracks, comparisons, or optional GPU. Keep each experiment tied to its live app/build identity; this skill describes the ALD app's bounded workflow, not generic model training.
